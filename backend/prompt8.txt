# Antigravity Prompt: AICTE Application Processing Backend and Detailed Status Tracking

## 1. Project objective

I am building an AICTE workflow management platform with two existing account types:

1. Institute User
2. AICTE Member

The institute-side application submission and document upload flow is being implemented separately. Now I want to implement the **AICTE-side application-processing backend and its database integration**.

When an institute submits an application, the application must appear in the appropriate AICTE processing queue. Authorized officers and committee members should be able to open the application, view all submitted fields and documents, perform their permitted actions, submit findings, and move the application to its next stage.

The most important feature is **detailed, persistent application status tracking**. For every application, I must be able to see exactly what has happened, what is happening now, who is responsible, what documents and reports exist, why the application is pending, and what must happen next.

## 2. Inspect the existing project first

Before writing code:

- Inspect the current frontend and backend structure.
- Identify the actual database and its existing tables.
- Inspect the authentication and authorization implementations.
- Inspect the existing application submission, application documents, synthetic staff dataset, committee memberships, roles, permissions and workflow assignments.
- Reuse existing models and API routes whenever possible.
- Identify any missing relationships instead of creating duplicate tables unnecessarily.

Keep the existing JavaScript, Node.js, Express and SQL/SQLite architecture. If the project uses Prisma, follow its existing conventions. Do not introduce TypeScript or a new framework.

Do not rebuild the institute-side application form or document-upload system if it already works. Connect it properly to the AICTE processing workflow.

## 4. Support the following application and case categories

Use the process definitions I supplied as the initial MVP requirements.

### Chapter 1 — New Institution Approval

Implement configurable stages for:

1. Application submission and fee verification
2. Scrutiny Committee
3. Re-Scrutiny, when required
4. Expert Visit Committee (EVC)
5. Executive Committee (EC) decision
6. Security deposit / Letter of Approval, where applicable
7. Appeal through SAC and Council, when eligible

Expected branches:

- Successful initial scrutiny advances to the next configured stage.
- A scrutiny deficiency creates a recorded deficiency and a re-scrutiny or compliance step, according to the configured workflow.
- A failed re-scrutiny records its findings and follows the applicable decision route.
- EVC records its observations and recommendation.
- The authorized decision-making body records the decision and its reasons.
- An eligible appeal creates a separate appeal record linked to the original application.

Do not treat a recommendation as the final approval decision.

Support configurable stages for:

Each application must have several distinct fields:

- Overall application status
- Current workflow stage
- Current stage status
- Current assigned user or committee
- Submission date
- Last action date
- Next action required
- Pending with
- Decision status, if a decision has been made
- Closure date, if applicable

Use a consistent status model. For example:

**Overall statuses**

- DRAFT
- SUBMITTED
- IN_PROGRESS
- AWAITING_INSTITUTE
- AWAITING_AI CTE_ACTION
- DECISION_PENDING
- APPROVED
- REJECTED
- WITHDRAWN
- CLOSED

Correct the spelling of the identifier to `AWAITING_AICTE_ACTION` in code.

**Stage statuses**

- NOT_STARTED
- PENDING_ASSIGNMENT
- ASSIGNED

- DEFICIENCY_RAISED

- DECISION_RECORDED
- COMPLETED
- SKIPPED

Add more statuses only when needed. Do not treat a stage passing as the same thing as the overall application being approved.

## 7. How an application enters the AICTE workflow

When an institute submits an application, the existing backend should trigger the following logic:

1. Verify that the submission exists and was successfully saved.
2. Verify that the required application data and documents are complete.
3. Verify the payment state when payment is required.
4. Change the application from draft/submitted state to the appropriate processing state.
5. Identify the application's type and workflow definition.
6. Create a workflow instance associated with the application.
7. Create the initial workflow stage and history entry.
8. Determine the eligible processing queue or committee.
9. Create a workflow assignment using active role permissions, committee membership and application assignment rules.
10. Make the application visible in the authorized AICTE queue.
11. Record the event in the audit log.

Use database transactions for operations that must succeed or fail together.

Do not create multiple workflow instances when an institute retries the submission request.

If an assignment fails, keep the application in a valid pending-assignment state and record the problem instead of losing the submission.

## 8. Staff assignment and authorization

Resolve the eligible reviewer or committee using:

- Active staff account
- Active committee membership, where required
- Appropriate platform permission
- Applicable jurisdiction or region, if configured
- Relevant application stage
- Active workload/assignment state, if used by the MVP allocation logic

Create a persistent assignment record linking the application, workflow stage, assigned committee and assigned member as appropriate.

For the prototype, an automatic assignment algorithm may be used, but label it as simulated allocation logic. Do not claim that the exact production AICTE allocation algorithm is known.

An officer must only perform permitted actions on applications they are authorized to access.

A Super Admin's platform-management permissions must not automatically confer statutory application-approval authority.

## 11. Workflow configuration

Implement configurable workflow templates for each application type and subtype.

A workflow stage should contain information such as:

- Stage key
- Display name
- Sequence or transition rules
- Eligible roles/committees
- Required inputs or documents
- Allowed outcomes
- Next stage for each outcome
- Whether the stage is conditional
- Whether the stage can be skipped, and under what approved condition
- Whether the stage requires a decision document

Example:

Scrutiny outcome `PASS` → configured next stage.

Scrutiny outcome `DEFICIENCY` → create deficiency and route to the applicable response/re-scrutiny stage.

Scrutiny outcome `FAIL` → follow the configured authorized decision route.

Do not assume every stage has only a pass/fail result. Some stages produce recommendations or request compliance, and final decisions may belong to a different authority.

Use configuration tables or structured seed data rather than embedding all workflow rules in large controller functions.

## 12. Important security and consistency requirements

- Enforce authorization in the backend, not merely by hiding frontend controls.
- Never trust user IDs, roles, committee IDs or permissions supplied by the client.
- Restrict Institute Users to their own institution's applications.
- Restrict AICTE members to their assigned applications and authorized queues.
- Protect application files through authenticated access.
- Validate all stage transitions on the server.
- Use transactions where status changes, assignments and audit entries must stay consistent.
- Ensure repeated submission requests are idempotent.
- Do not fabricate reviewer actions, inspection results or official decisions.
- Do not allow an unauthorized employee to approve or reject an application by changing a request payload.
- Do not delete previous reports or document versions when a new version is submitted.
